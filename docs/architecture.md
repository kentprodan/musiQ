# musiQ — Target Architecture

## Why this shape

musiQ unifies tag editing (Mp3Tag), local library management (MusicBee/iTunes),
and self-hosted streaming (Plexamp) behind one Rust core, with a genuinely
native UI shell on every target OS — no cross-platform UI toolkit, no shared
webview chrome. Three options were considered and rejected:

- **A single cross-platform UI framework** (Flutter, React Native, MAUI) —
  would sacrifice the one hard requirement: pixel- and interaction-perfect
  adherence to each platform's current design language (Fluent 2, Liquid
  Glass, Material 3 Expressive, Libadwaita, Breeze).
- **Tauri everywhere** — same problem in a different shape: a shared
  HTML/CSS/JS shell can *approximate* native materials (as the previous
  iteration of this repo did, via `data-os` CSS tokens) but never reaches
  real native controls, animations, or accessibility behavior.
- **Fully independent apps per OS with no shared code** — would multiply
  every piece of business logic (library scanning, tag read/write, remote
  sync protocols) by the number of target platforms.

## The shape

```
musiQ/
├── core/musiq-core/     Rust — all business logic, no FFI attributes
├── ffi/musiq-uniffi/     UniFFI adapter crate (cdylib), depends on musiq-core
├── clients/
│   ├── windows-winui/    WinUI 3 (Fluent 2) — Windows desktop
│   ├── apple-native/     SwiftUI (Liquid Glass) — macOS/iOS/iPadOS/tvOS/watchOS/visionOS/CarPlay
│   ├── android-native/   Jetpack Compose (Material 3 Expressive) — phone/tablet/TV/Wear OS
│   ├── linux-gnome/      GTK4 + Libadwaita — GNOME
│   ├── linux-kde/        Qt/Kirigami — KDE Plasma
│   └── desktop-tauri/    Interim engine for macOS/Linux desktop until their native clients exist
├── bindings/             Generated Swift/Kotlin/C# bindings — git-ignored, never hand-edited
└── scripts/              Binding-generation scripts (one per consuming language)
```

One Rust core (`core/musiq-core`) owns every piece of business logic:
SQLite persistence, tag read/write, library scanning, and — in later
phases — the audio playback engine, Plex/Subsonic/Navidrome clients, and
the sandboxed plugin host. It exposes no FFI surface itself; `rusqlite`
connections and other non-`Send`/non-`Sync` internals stay fully
encapsulated.

`ffi/musiq-uniffi` is a thin `cdylib` adapter around `musiq-core`, written
against [UniFFI](https://mozilla.github.io/uniffi-rs/)'s modern proc-macro
API (`#[derive(uniffi::Record/Object/Error)]`, `#[uniffi::export]`) rather
than the legacy `.udl` file. This one contract is the single FFI boundary
every native client crosses:

- **Swift** (Apple platforms) and **Kotlin** (Android) — generated directly
  by `uniffi-bindgen`, UniFFI's officially supported targets.
- **C#** (Windows) — generated by the community `uniffi-bindgen-cs`
  generator ([NordSecurity](https://github.com/NordSecurity/uniffi-bindgen-cs)),
  pinned to the `uniffi` version it targets for contract compatibility.

No client contains its own copy of business logic; every client is a UI
shell that calls into `musiq-core` only through this one generated
contract.

## Desktop: Tauri as an interim bridge, not the destination

Windows gets a fully native WinUI 3 client starting now (see
`clients/windows-winui/`). macOS and Linux desktop remain on the interim
Tauri/React engine (`clients/desktop-tauri/`, not rebuilt in this pass)
until their own native clients — SwiftUI for macOS, GTK4/Libadwaita for
GNOME, Qt/Kirigami for KDE — are built. Tauri is deliberately not part of
the long-term architecture; it exists only to keep those platforms usable
while native shells are developed one at a time.

## Status

Phase 1 (this pass) built the minimal Rust core plus the Windows WinUI 3
shell. Every other `clients/*` folder aside from `windows-winui` is a
placeholder README describing what will eventually live there — no code,
so nothing here misrepresents what's actually been built.
